# 메모리 보호와 단일 모델 실험

검증일: 2026-11-08, Asia/Seoul. 기존 작업과 경기 규칙·캐릭터·통계를 유지하며 실험실 경로를 확장했다.

## 기존 차단 조건과 조사

기존 `Ollama.guard()`는 다음 중 하나면 실행 전에 무조건 보류했다.

1. 모델 파일 크기 > 4GiB 이면서 기존 스왑 > 2GiB
2. psutil 가용량 < 모델 파일 크기 × 1.12 + 0.4GiB
3. 스왑 통계를 읽을 수 없음

추론 중에는 가용량 < 0.3GiB 또는 시작 대비 스왑 사용량 +1GiB만으로 중지했다.

문제는 저장된 파일 크기 기반 예상값과 이미 존재하던 스왑을 현재의 실제 메모리 적합성처럼 사용한 것이다. 기존 스왑은 앱이 종료돼도 바로 줄지 않을 수 있고 현재 압박과 같지 않다. 모델 크기는 파일/양자화/컨텍스트/런타임/GPU 버퍼에 따라 실제 로드 비용과 다르다.

또한 기존 `used_gb = total - available` 표시는 psutil의 macOS `used`와 다른 값이었다. 설치된 psutil 7.2.2의 소스를 확인하면 macOS에서 `available = inactive + free`, `used = active + wired`다. 새 측정은 psutil `used`, `available`, `free`, `active`, `inactive`, `wired`를 별도로 기록하고 `total - available`은 `unavailable_gb`로 구분한다. Activity Monitor의 압축 메모리를 포함한 ‘메모리 사용’과 완전히 같은 숫자라고 주장하지 않는다.

압박 판단에는 macOS `kern.memorystatus_vm_pressure_level`을 읽는다. 이 sysctl은 XNU 내부 enum(0/1/2/3)이 아니라 NOTE/DISPATCH 플래그 **1=normal, 2=warning, 4=critical**을 반환하므로 내부 enum과 혼동하지 않았다. 읽지 못하면 unknown으로 표시한다.

근거:

- [Apple Activity Monitor 메모리 안내](https://support.apple.com/en-ie/guide/activity-monitor/actmntr1004/mac): 가용 메모리뿐 아니라 스왑 속도·wired·캐시 등을 함께 설명한다.
- [Apple XNU 메모리 압박 알림 문서](https://github.com/apple-oss-distributions/xnu/blob/main/doc/vm/memorystatus_notify.md)
- [Apple sysctl 알림 변환 구현](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_memorystatus_notify.c), `convert_internal_pressure_level_to_dispatch_level` 및 `sysctl_memorystatus_vm_pressure_level`
- 현재 설치된 psutil `_psosx.virtual_memory()` 구현; [psutil 공식 문서](https://psutil.io/)

## 현재 정책

### 경고: 사용자가 실험실에서 1회 확인 가능

- 파일 크기 기반 참고 예상량보다 가용량이 적음
- macOS 압박이 warning

예상량은 기존 기준(파일 GiB × 1.12 + 0.4)에 2K 초과 컨텍스트의 작은 참고 여유분을 더한 **휴리스틱**이다. 실제 RAM 요구량이 아니다. 기존 스왑 2GiB 초과만으로는 더 이상 차단하지 않고 참고 정보로 표시한다.

실험실의 ‘메모리 점검’ → 경고 확인 → **위험을 감수하고 1회 실행**을 선택하면 한 모델의 한 프롬프트만 실행한다. 서버도 모델 1개/상황 1개로 범위를 검사하고 재시도 횟수를 0으로 고정한다. 동의는 요청에만 존재하며 다음 요청이나 게임 설정에 저장되지 않는다. 게임 시작과 에이전트 호출에는 이 예외가 자동 적용되지 않는다.

### 우회 불가 / 실행 중에도 감시

- macOS 압박 critical
- 가용량 ≤ 0.20GiB
- 압박과 스왑을 모두 읽지 못하면서 가용량 < 0.60GiB
- 실행 중 스왑이 시작 대비 1GiB 넘게 증가하고 동시에 가용량 < 0.50GiB

0.5초 간격으로 시스템을 관찰한다. 위 조건이면 요청 스트림을 취소하고 언로드한다. 이 하한은 앱의 비상 중지 기준이며 OOM을 완벽하게 예방한다는 보장은 아니다. 다른 앱도 같은 시스템 메모리를 공유하므로 모든 변화가 해당 모델 때문이라고 단정하지 않는다.

다른 태그가 이미 로드돼 있으면 새 모델을 호출하지 않는다. 같은 모델 한 개만 남아 있으면 재사용할 수 있다. 앱은 하나의 추론 잠금으로 게임과 실험 요청을 직렬화한다. 모든 생성 요청은 `keep_alive:0`이며 성공·실패·사용자 중단 후 모두 별도 언로드와 `/api/ps` 확인을 수행한다. 해제를 확인하지 못하면 후속 실행을 보류한다. 다른 앱의 Ollama 동시 요청까지 앱의 잠금이 통제할 수는 없다.

## 실험 결과 구분

| outcome | 의미 |
|---|---|
| deferred | 설치/메모리/런타임 점검에서 보류, 생성 요청 없음 |
| success | 실제 최종 출력 수신 |
| failed | 실제 Ollama 호출/로딩/추론/응답 검증 실패 |
| cancelled | 사용자가 중단; 스트림 종료와 언로드 후 기록 |
| emergency_stopped | 실행을 시도했지만 비상 메모리 조건으로 자동 중지 |

모델 하나의 보류/실패가 다음 모델의 점검을 막지 않는다. 일반 모드는 네트워크/HTTP/시간 초과에 한해 설정 범위 내 최대 1회 재시도하며 OOM·메모리 보류·언로드 실패는 자동 재시도하지 않는다. 위험 확인 실행은 항상 재시도 0회다. 실험실 중단 버튼은 관리자 인증 후 현재 배치를 중지한다.

기록에는 정확한 태그/digest, 실제 요청 시도 여부, 단계, 오류 코드, 출력, 토큰/로딩/첫 토큰/전체 시간, 모드, 시스템 메모리 표본, 스왑 변화, 언로드 확인을 보관한다. SQLite에 저장하되 공식 경기 승률에는 포함하지 않는다. 내부 추론은 저장하지 않는다.
